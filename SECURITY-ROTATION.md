# Rotations manuelles obligatoires avant production

Aucune rotation externe n'a été effectuée par cette branche. Tout secret ayant figuré dans un ancien `.env` Git est compromis, même si le HEAD est propre. Ne pas coller les anciennes/nouvelles valeurs dans un ticket, une PR ou les logs.

1. **JWT** : générer une clé cryptographiquement aléatoire d'au moins 32 octets, encodée Base64, dans votre gestionnaire de secrets. Remplacer `GROUPIA_JWT_SECRET_BASE64` sur toutes les instances puis redéployer. Les JWT existants deviennent invalides : prévoir une reconnexion des organisatrices.
2. **Cloudflare** : dans Zero Trust / Networks / Connectors (Tunnels selon votre interface), sélectionner le tunnel Groupia, renouveler son token, mettre à jour `CLOUDFLARED_TUNNEL_TOKEN` dans le déploiement et redémarrer les connecteurs. Après la rotation du token compromis, forcer la déconnexion de toutes les anciennes connexions, puis vérifier les connecteurs attendus et les journaux d'accès ([procédure Cloudflare](https://developers.cloudflare.com/tunnel/reference/tunnel-tokens/)). Ne pas recréer un tunnel au hasard.
3. **Bictorys** : dans le compte et l'environnement appropriés (sandbox et production séparés), renouveler/révoquer l'API key, la private key et le webhook secret. Si ces opérations ne sont pas proposées dans votre dashboard, les demander au support Bictorys. Mettre à jour `BICTORYS_API_KEY`, `GROUPIA_BICTORYS_PRIVATE_KEY` (et tout ancien `BICTORYS_PRIVATE_KEY`), `BICTORYS_WEBHOOK_SECRET` et les éventuels secrets merchant/payout/subscription configurés. Coordonner l'activation du nouveau secret webhook côté Bictorys et Groupia ; prévoir la réconciliation des événements reçus pendant la bascule. Vérifier un paiement contrôlé et la corrélation intégrale, sans forcer de statut SQL.
4. **Meta / WhatsApp** : dans Meta Business Settings / System Users, révoquer le token exposé, générer un nouveau token pour l'application et les seuls actifs/permissions WhatsApp nécessaires, puis le stocker dans `GROUPIA_WHATSAPP_ACCESS_TOKEN`. Vérifier un envoi contrôlé avec un template approuvé. Ne jamais changer les contrats de templates au hasard.
5. **Autres secrets** : renouveler le mot de passe PostgreSQL et tout certificat privé exposé ; révoquer les sessions/accès concernés. Pour `GROUPIA_CUSTOMER_MAGIC_KEY_BASE64` et `GROUPIA_CUSTOMER_OTP_PEPPER_BASE64`, suivre les noms exacts de `.env.example` et planifier l'invalidation des liens/OTP en cours. Vérifier les noms effectifs dans la configuration avant déploiement.
6. **Nouveaux secrets locaux au déploiement** : générer une clé indépendante `GROUPIA_AUTH_RATE_LIMIT_KEY_BASE64` (32 octets minimum Base64) et un token de collecte `GROUPIA_MONITORING_TOKEN` (au moins 32 caractères aléatoires). Même clé HMAC sur toutes les instances. Les stocker séparément de la clé JWT. Aucun exemple de valeur fonctionnelle n'est livré.
7. **GitHub** : activer secret scanning/push protection si disponible, Dependabot alerts, revue obligatoire et checks CI requis sur `main`. Examiner les accès au dépôt et les anciens artefacts contenant `.env` ; supprimer/révoquer les copies selon votre procédure. Cette tranche ne réécrit pas l'historique et ne force-push pas.

Conserver la date, le responsable, la référence du secret dans le coffre, la preuve de révocation et le résultat du contrôle pour chaque rotation, jamais sa valeur. Un scan HEAD vert ne valide pas les secrets déjà divulgués dans l'historique.

Référence Meta : [collection officielle Cloud API et accès System User](https://www.postman.com/meta/whatsapp-business-platform/collection/wlk6lh4/whatsapp-cloud-api).
